# Narrated video verification

Deliver a reviewable video of **real application footage** proving the current change works across its full blast radius, accompanied by coverage, limitations, and assigned follow-up tasks. Use English narration unless requested otherwise. Default voice: OpenRouter **`elevenlabs/eleven-multilingual-v2` / `george`**.

Perform the workflow within the requesting user's authorization and repository rules. Confirm the scope of paid speech generation, public publication, tracker writes, fixture writes, code fixes, and staging deployment from the actual request and environment; do not inherit another user's personal pre-approvals. This workflow does not itself authorize production writes, merging, production deployment, unrelated fixes, or Slack/email messages. For a narrower request, honor that request's actual scope.

Follow repository instructions and relevant feature docs. If staging deployment is needed, follow the repository's established review and deployment workflow. The production guide and both Python helpers are included in this skill directory. Resolve supporting paths relative to this `SKILL.md`, not the caller's working directory. See the repository README for prerequisites and installation.

## Define and verify the blast radius

1. Inspect the diff, base/head revisions, feature contracts, shared consumers and target build. Expand the checklist to all affected entry points and adjacent paths sharing the changed machinery. Include normal behavior, failure/retry limits, authorization where relevant, boundary data, and persistence after full reload. Exercise actual writes when affected; a read-only happy path does not cover writes.
2. Write a coverage matrix before filming. For each scenario record expected outcome, target surface, fixture ownership, ready signal, assertions, and proof type: browser, deployed API/runtime, or local test. Don't report backend diagnostics or local simulators as live browser coverage. Distinguish expected safe rejection from a defect.
3. Confirm the running build contains the intended changes. On shared staging record the build at start and end and verify it did not change during the run. A build change requires a fresh coherent run. Use base-branch controls in a separate local worktree when practical; don't roll shared staging backwards. Same-build controls are not a previous-build A/B comparison.
4. Authenticate in a **non-recorded** context, then create the recording context from in-memory auth state. Keep cookies and credentials outside every served directory. Use owned synthetic fixtures, including expendable sources for deletion controls. Record at a legible fixed viewport, retaining the original video untouched. Close the browser context to finalize it.
5. Drive actual controls with real pointer/keyboard actions. Wait for domain-specific ready states, scope ambiguous selectors, and assert outcomes. Do not bypass a broken button with force-click, DOM mutation or hidden APIs and call the UI passed. Test workarounds/backend fixture operations separately and retain the original failure.
6. Re-check mutations after full reload. Capture and **open/inspect** screenshots for distinct outcomes and reloads. Record precise raw-video offsets and UTC timestamps per scenario, with assertion evidence. Collect page/console errors, failed requests, HTTP failures, and GraphQL errors inside HTTP200 responses. An accessibility label is not necessarily visible wording.
7. Bracket the run with relevant backend logs/traces. Use the project's configured observability tools and issue-tracker integrations. Include client HTTP5xx spans that may have `ok` span status. Count errors without excluding records lacking optional facets. Correlate intentional failures and disclose unattributed shared-environment errors; zero pageerrors does not establish clean telemetry.

For a substantial multi-surface run, one browser subagent may execute the checklist while the parent owns code, deployment, tracker writes and telemetry. Give exact routes, fixtures, revision, assertions, output paths and credential-handling requirements. Avoid concurrent writers in one account. The parent reviews evidence and reconciles gaps.

## Bugs determine the next step

**In scope:** Reproduce and distinguish product failure from harness/timing error. Fix the smallest underlying issue consistent with the task, add meaningful regression coverage when warranted, run relevant checks, and deploy to the chosen target. Then **restart from the diff and complete blast-radius checklist with a fresh recording of the final build**. Earlier clips are diagnostic material, not passing evidence for the new build. Repeat until no actionable in-scope defects remain. If access, authorization or an external dependency prevents progress, report the concrete blocker and remaining checks; don't issue a success verdict or loop without new evidence.

**Out of scope:** Reproduce enough to file an actionable task; do not quietly broaden the implementation. Use the project's tracker (through the project's configured integration). Search for duplicates and resolve **the requesting user's tracker identity**; the integration's authenticated account may be different. Create the task assigned to the user, or reuse a matching task already assigned to them. If an existing task has another owner, preserve their assignment and create a linked follow-up assigned to the user where needed. Select the owning team/project from repository/issue context. Read back the task to verify assignee and URL.

Tasks include actual vs expected behavior, reproduction, build/viewport, frequency, scope rationale, workaround, and sanitized evidence. Don't claim a defect is pre-existing without a baseline. File useful evidence first, reference the video chapter after publishing (include the keyed link only if the user asked to share it there), and list **every** out-of-scope finding beside the video with task link and assignee. Label unresolved investigations and coverage gaps separately. If tracker access/identity is blocked, retain a ready-to-file payload and explicitly report filing as incomplete; don't invent a link or report an unassigned task as done.

## Edit and narrate the verified result

Read [the production guide](references/production.md) for capture, speech, editing, diagram and hosting mechanics. Use its helpers where appropriate; the agent owns behavioral assertions and editorial/evidence review.

### Required structure

1. **Opening chapter: the bug and its root cause.** Before any verification footage, state in plain language: what the user or system saw (symptom, where, when, impact), the root cause (the actual mechanism, with the component names), and what the fix changes. Keep it short (about 30–60 seconds). Use only established facts; if the root cause is partly unproven, say which part is confirmed and which is a hypothesis. For a change that is not a bug fix, summarize the problem the change solves instead.
2. **Explanatory diagrams for invisible backend behavior.** When the fix changes backend behavior that the recorded UI cannot show (workers, jobs, retries, locks, leases, ownership, queues, network calls, database state, deploy machinery), add an animated diagram chapter after the summary and before the footage. Show the failing sequence first (actors, messages/calls, state changes, and the exact point where it went wrong), then the fixed sequence with the changed step highlighted. A frontend-only fix needs no diagram unless the cause is otherwise hard to follow.
3. **Verification footage** as below, then the verdict, limits and follow-ups.

**Bug introduction history:** In the root-cause explanation and matching written summary, include what is known about when the bug appeared and how it was introduced. Distinguish the earliest observed failure from the actual introduction. When supported by evidence, identify the relevant commit, PR, deployment, configuration or dependency change, give its date/version, and explain how it caused the failure. If the introduction date or mechanism is unknown or only suspected, say so explicitly and separate that uncertainty from the confirmed root cause. Do not treat an alert timestamp or a nearby change as proof of introduction. Use available investigation evidence; this does not require an exhaustive historical investigation before publication.

Diagrams are explanations, not evidence. Derive every actor, step and state from the actual code, the diff, and the reproduction/telemetry evidence; name real modules/functions/services, not invented components. Label each diagram frame clearly as `Diagram — not app footage` (or equivalent), and keep its visual style distinct from the application UI so that no viewer can mistake it for the product. Never use a diagram to stand in for missing verification; when a backend effect is verified, show its real proof (deployed API/runtime result, log or trace excerpt, test output) next to or after the diagram, labelled with its proof type.

### Footage and narration rules

- Edit genuine raw clips of the **final verified build**. Preserve originals and an edit list mapping each clip to raw file/time/build. Never fabricate UI, replay a mock as the real app, replace failure with success imagery, or alter application content in post-production. Label screenshots, diagnostic cards, local tests, shortened waits, speed changes and held frames.
- Show the app at a readable scale. For small details, prefer a clear cut from the full view to a labelled close-up, then return to context. Do not place an enlarged copy over the same visible UI: duplicate cards, panels or dialogs can look like nested app content. If simultaneous context is needed, use separate, bordered regions with explicit labels and space between them. Preserve source pixels/aspect ratio and keep the action and result visible. Uncut footage may go in the export; the access key protects it.
- Use animated zoom only when it helps the viewer locate a detail. Make the move brief and the scale change clear, then hold a readable view. Avoid slow, barely perceptible zooms or motion stretched across a narration segment. Review the rendered transition at normal playback speed; use a cut if the motion adds no useful information.
- When a control, changed value or outcome is hard to locate, add a brief circle, outline, arrow or highlight. Mark it clearly as an editorial annotation and keep the target visible. Track moving targets, remove the cue after it serves its purpose, and never cover text, controls or error evidence. Review annotations at the delivered size; do not mark every action or imply an app state that the footage does not show.
- Narrate only what evidence establishes, including expected rejection and limits. Distinguish hidden retries proved by runtime events from valid first responses. A screenshot doesn't establish a backend write; a deterministic test isn't staging behavior. Explain material out-of-scope issues rather than editing them out of the verdict.
- Generate per-chapter speech through OpenRouter with the exact default model/voice above. Use a key already configured in `OPENROUTER_API_KEY`, or supply a private credential file with `--key-file`; do not include any key in this document. Pass it directly to the process; never put it in scripts, commands, logs, reports or the repository. If unavailable, surface the error instead of silently substituting a voice. Keep credential-free receipts, model/voice, exact script and generation provenance.
- Narration is sent to OpenRouter and appears in the captions behind the access key. Use only content authorized for those destinations. Remove credentials, secrets, customer or third-party content, user identities or emails, and private data unless their use is explicitly authorized and appropriate. No personal pre-approval is bundled with this document.
- Export browser-compatible H264/yuv420p MP4 with AAC narration and `+faststart`, chapters, captions and editable script. Normalize speech around -16 LUFS, true peak at or below -1.5dB. Preserve legibility. Inspect rendered frames at every zoom/failure and verify narration matches footage. Disclose approximate caption timing if used.

## Publish and validate the actual link

Build a mobile-friendly report with playable video first, a short written bug/root-cause/fix summary matching the opening chapter, chapters, MP4 download, captions/script, coverage matrix (pass/fail/expected-rejection/partial/skipped), build/window, evidence, telemetry classification and limits. Put assigned out-of-scope task links **alongside the video**, not only in hidden JSON. Include fixed in-scope bugs and final retest results. Never give a false all-green tally.

Publish an explicitly selected **export directory**, not the working artifact directory. Exclude auth state, cookies, secrets, raw logs and diagnostic scripts; protect the private run directory with mode 0700. **Do not blur, crop or otherwise redact the footage.** The access key, not redaction, protects the video and report, so show the app as recorded. The one exception is a live credential (API key, password, session token) in a frame: the link can be forwarded, so recapture without it, or quarantine that original, exclude it from the export and follow the established rotation process with the necessary authorization. State what the video contains.

Serve the export with the bundled `scripts/serve.py`. It generates an unguessable access key (`secrets.token_urlsafe(32)`, 256 bits) and serves files only below `/<key>/`; every other path returns 404. Pass `--key-file` with a mode-600 file in the private run directory so a restart keeps the same key. Then run **`cloudflared tunnel --url http://127.0.0.1:<port>`** for a `https://…trycloudflare.com` hostname. Publish when authorized by the requesting user; do not infer authorization from this shared document alone. The link to deliver is `https://<host>.trycloudflare.com/<key>/`; the bare hostname is not a link. Keep the key out of every file in the export, and out of commits, tracker tasks, PRs and chat channels unless the user asks to share it there. Keep both processes alive after the tool call and final reply, recording PIDs/log paths privately. Verify the **keyed** URL in a browser: actual playback advances, seeking works, captions/downloads load, and byte ranges return HTTP206. Verify that the bare hostname and a wrong key return 404. Check phone layout. A localhost/LAN URL or HTTP200 alone is insufficient. Quick Tunnels work only while this machine and both processes remain online; say so instead of promising durable hosting. A Cloudflare challenge/login page is not verified playback.

After publication attach evidence links to filed follow-ups only if the user asked to share the key there; otherwise reference the chapter by name. Verify assignments again. End with the full keyed watch URL, the keyed MP4 download URL, concise result/limits, and out-of-scope task links with assignee. If hosting or issue filing failed, deliver completed artifacts and identify the unfinished part.
